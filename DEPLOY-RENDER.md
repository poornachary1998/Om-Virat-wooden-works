# Deploying Strapi to Render

This repo now ships with everything Render needs: `strapi/Dockerfile` builds a
production Strapi image, and `render.yaml` (at the repo root) is a Render
**Blueprint** that provisions a Postgres database, a web service running that
Dockerfile, and a persistent disk for uploaded photos.

Locally verified before committing: `npm ci`, `NODE_ENV=production npm run
build`, and `npm run start` all succeed in `strapi/`, and `/_health` returns
`204`.

---

## One-time setup on Render

1. Push this branch to GitHub (already done if you're reading this from the repo).
2. In the Render dashboard: **New +** → **Blueprint**.
3. Connect the `poornachary1998/om-virat-wooden-works` repo. Render will detect `render.yaml` at the root.
4. Review the plan: it creates
   - a Postgres database (`om-virat-strapi-db`, `starter` plan, Singapore region)
   - a web service (`om-virat-strapi`) built from `strapi/Dockerfile`, with a 1GB disk mounted at `/opt/app/public/uploads` for media
   - all required secrets (`APP_KEYS`, `ADMIN_JWT_SECRET`, `API_TOKEN_SALT`, `TRANSFER_TOKEN_SALT`, `JWT_SECRET`, `ENCRYPTION_KEY`) auto-generated by Render — you never type these in
   - `DATABASE_URL` wired automatically from the database to the web service
5. Click **Apply**. First build takes ~5-10 minutes (it compiles the admin panel).
6. Once live, open `https://<your-service>.onrender.com/admin` and create your admin account — same as the local flow in `LOCAL-SETUP.md`.

The content types (`Product`, `Category`, `Site Setting`) are already committed
under `strapi/src/api/`, so they show up immediately — no manual copy step
needed like in local dev.

## After first deploy

1. **Open the API** — Settings → Users & Permissions → Roles → Public → tick
   `find`/`findOne` for Product, Category, Site-setting, and Upload. Same step
   as local setup, just on the live URL.
2. **Seed content** — from your machine: `cd cms/seed`, point `.env` at
   `STRAPI_URL=https://<your-service>.onrender.com` with a fresh API token
   from the live admin, then `npm run seed`.
3. **Point the frontend at it** — on Vercel, set
   `NEXT_PUBLIC_STRAPI_URL=https://<your-service>.onrender.com`.
4. **Lock down CORS** (recommended) — `strapi/config/middlewares.ts` currently
   uses Strapi's default `strapi::cors`, which reflects any request origin.
   Once you know your Vercel domain, restrict it:

   ```ts
   {
     name: 'strapi::cors',
     config: { origin: ['https://your-site.vercel.app'] },
   },
   ```

   Ask me to make this change once you have the final domain and I'll wire it
   up along with the env-based fallback for local dev.

## Notes / things worth knowing

- **Plans**: `render.yaml` uses the `starter` plan for both the web service
  and the database (not free) because Render's free web service tier sleeps
  after inactivity and doesn't support persistent disks — you need at least
  Starter for uploaded photos to survive restarts and for the CMS to stay
  responsive. Roughly matches the ₹400–800/month estimate in `README.md`.
- **Uploads persistence**: media goes to the mounted disk. If you ever move
  to Cloudinary/S3 instead (mentioned as an option in `README.md`), the disk
  becomes unnecessary — say so and I'll swap the upload provider config.
- **Blueprint fields**: Render's Blueprint YAML schema can change over time.
  If `render.yaml` fails to parse in the dashboard, check Render's current
  [Blueprint spec docs](https://render.com/docs/blueprint-spec) for any
  renamed fields — this file couldn't be validated against Render's live
  docs from this environment (network egress to render.com is blocked here),
  only against the Strapi app itself.
- **Zero-downtime rebuilds**: `autoDeploy: true` means every push to this
  branch triggers a new Render deploy automatically.
